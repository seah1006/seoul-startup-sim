# 이벤트 밸런스 보고서 (TASK-007B)

전환점 빈도 점검과 조정 기록. 숫자 표는 `EventBalanceSimulationTest`가 아래 표식 사이를 자동으로 교체한다.

## 재현 방법

```
cd backend
gradlew.bat simulate --tests "*EventBalanceSimulationTest" --offline
```

- 메인 DB(5433)에 읽기 전용 세션(JDBC readOnly + `SET default_transaction_read_only = on`, `SHOW`로 on 확인)으로 SELECT만 실행한다. 읽는 것: `game_settings`, `service_industries`, 매출·점포·상권 조인, 활성 전환점·반응·순간 정의. DDL/DML·Flyway 실행 없음.
- "조정 전"은 측정 시점 메인 DB의 정의(V8 시드 그대로, 모든 정의 rev 1)다. "조정 후"는 같은 정의에 `V12__event_tuning.sql`의 전환점 UPDATE 문을 정규식으로 읽어 적용한 값이다. 시뮬레이터와 마이그레이션 값이 따로 놀지 않는다.
- 발생 판정은 `EventEngine.judge`를 그대로 호출하고, 후보 선택(가장 높은 priority 묶음에서 균등 추첨)·성공 판정(`TURNING_POINT_SUCCESS` 스트림)·순간·반응 개수·가상 경쟁점은 서비스 코드와 같은 난수 스트림으로 메모리에서 재현한다. 효과(현금·능력치·보정·플래그·매장 수·경쟁점)는 메모리 상태에 반영해 다음 분기 계산과 조건에 들어간다.

## 판단 (V12 당시 기록)

- **조정 전 빈도는 목표의 약 1.7배였다.** 12분기 완주 게임 기준 평균 6.88회, 3~5회 구간은 12.5%뿐이었다. 전환점 12개 중 다수가 2~4분기부터 상시 조건(외식 업종, 직원 2명 이상 등)이라 분기마다 여러 개가 동시에 후보가 되고, 개별 확률 0.22~0.30이 겹쳐 분기당 발생 확률이 약 0.7이었다. 데모의 "8분기 중 5회"는 이 구조에서 자연스러운 값이다.
- **성공 확률은 표시대로 판정된다.** 모든 선택지에서 표본 성공률이 표시 성공률(화면의 반올림 %)과 ±5%p 안에 있고 전체 편차는 0.2%p 안팎이다. 엔진 버그는 없어 엔진 코드는 고치지 않았다. 데모의 "전부 성공"은 선택지 절반가량이 성공률 100%인 안전한 선택지이고(무작위 선택 시 전체 성공 비율 약 78%), 데모 선택 규칙(분기 번호 mod 선택지 수)이 그쪽에 자주 걸린 결과다.
- **조정(V12)**: 상시 조건 전환점의 기본 확률을 0.08~0.12로 낮추고, 반복 가능한 전환점(직원 이탈, 동네 축제, 크리에이터 협업, 시그니처 메뉴 화제)의 쿨다운을 8분기로 늘렸다. 직원 이탈은 게임당 최대 3회 → 2회. 성장 조건이 붙은 전환점(2호점, 재개발 소문)은 덜 낮췄다. 프랜차이즈 제안은 상권 순위 상위 30% 조건이 순위 공식(점포 수 ÷ 매력도)상 사실상 도달 불가라 0.8로 완화했다. 번아웃은 영업 14시간 이상 정책 전용이라 표준 정책에서는 0회가 정상이며 값은 그대로 두었다. `game_settings`의 이벤트 값은 바꾸지 않았다.
- **결과**: 완주 게임 평균 4.07회, 3~5회 구간 74.8%, 같은 전환점 반복 게임 1.9%(조정 전 27.0%). 순간(분기당 1개)과 반응(분기당 2~3개)은 설계대로라 조정 대상이 아니다.
- **V12 당시 한계: 연속 분기 발생.** 이전 분기에도 전환점이 있었던 비율이 74% → 50%로 줄었지만, 현재 엔진에는 "직전 분기에 아무 전환점이나 나왔으면 쉰다"는 전역 간격이 없다(쿨다운은 정의별, `event.fire.globalCap`은 분기당 최대 1개, `event.fire.cooldownDefault`는 엔진이 읽지 않음). 조건 DSL로 흉내 내려면 정의마다 다른 11개 정의의 `history.quartersSince`를 나열해야 해 관리자 편집이 어려워진다. **제안**: 엔진에 `event.fire.globalGap`(직전 전환점 이후 최소 분기 수) 설정을 추가하면 같은 평균 빈도로 연속 발생을 크게 줄일 수 있다. 지시서 범위(엔진은 버그일 때만 수정) 밖이라 구현하지 않았다.
- **골든 영향**: 004A 4분기 골든은 이벤트 정의를 비우고 돌아 영향 없음. 004B-1 이벤트 8분기 골든은 V12 정의로 돌리면 바이트가 달라진다(확인: 전환점 5회 → 4회, 20233 배달 앱 입점이 빠짐). 골든 파일은 그대로 두고 `GoldenEvents`(테스트 전용)가 V8 마이그레이션 파일의 콘텐츠 INSERT만 다시 실행해 정의를 고정하게 했다(`GoldenSettings`와 같은 방식). 두 골든 모두 통과.
- **표본 가정**: 사장님 능력치는 배경 4종 첫 후보, 집중은 가장 높은 둘, 정책은 표준 고정, 선택지는 균등 무작위. 실제 플레이어 분포는 반영하지 않았다. 실제 반경 경쟁점 대신 상권 점포 수 기반 기대치를 썼다.
## TASK-007C: 전역 간격과 효과 표기

- V13은 `event.fire.globalGap = 1`을 추가한다. 게임 생성 시 고정되는 settings 스냅샷에서 읽고, 키가 없으면 0으로 기존 동작을 유지한다. 마지막 전환점 발생 분기와 현재 분기의 차이가 1 이하이면 모든 정의의 발생을 막는다. 0이면 제한하지 않으며, 이력이 없으면 바로 후보 판정한다.
- 12분기 완주 게임 평균은 V12 4.07회 → 간격 1 적용 3.09회로 목표 3~5회 안이다. 따라서 V13에서는 확률을 보정하지 않는다. 조기 폐업까지 포함한 전체 평균은 3.03회 → 2.32회이며, 기존 목표와 동일하게 완주 게임을 기준으로 판단했다.
- 완주 게임 3~5회 비율은 74.75% → 76.07%, 직전 분기 연속 발생 비율은 49.80% → 0.00%다. 아래 전역 간격 비교 표는 V12와 V13을 순서대로 읽어 같은 표본에서 재현한다. 메인 DB는 읽기 전용 SELECT만 사용한다.
- 간격 기능만 적용한 상태에서 두 골든 테스트 16개가 파일·설정·이벤트 픽스처 수정 없이 통과했다.
- 선택 후 현금 및 ADD 금액 보정의 `effects[].value`도 `MoneyFormat.signedWon`으로 통일했다. 승인된 8분기 골든은 아래 4개 값만 변경되었다. 이 네 값을 원복한 JSON이 원본 파일 바이트와 같음을 확인했다. 4분기 골든과 GoldenSettings/GoldenEvents는 변경하지 않았다.
  - 2번 분기 항목: `-2,000,000원` → `-200만 원`
  - 3번 분기 항목: `+1,500,000원` → `+150만 원`
  - 4번 분기 항목: `+5,000,000원` → `+500만 원`
  - 7번 분기 항목: `+2,500,000원` → `+250만 원`
  - 항목 번호는 JSON 배열의 0 기반 인덱스이며 모두 `effects[0].value`다.

- `EventBalanceSimulationTest`는 MAJOR 판정 후 후보가 없을 때 실제 엔진의 `pickMinor`를 호출한다. MINOR는 별도 난수 스트림·DATA 우선·게임별 DATA 상한을 그대로 사용한다.
- MAJOR 선택 봇은 기존 균등 정책을 보존한다. MINOR 봇은 `p × 성공효과 + (1-p) × 실패효과`의 최대값을 고른다. 동점은 선택지 순서로 고정한다.
- 효과 환산은 현금 그대로, 능력치 1당 15만 원, 매장 1곳 1천만 원, 수정치 100%·1분기당 1천만 원 기준이다. 비용·임대료 수정치는 부호를 반대로 계산한다. FLAG/TEXT/경쟁점 효과는 점수 0이다. 이는 비교 가능한 **봇 휴리스틱**이지 실제 수익 예측이나 최적 정책 보장이 아니다.
- DATA 입력은 활성 버전 매출·점포·길단위인구의 전분기 비교다. 원본 결측·0 분모는 실제 엔진과 같이 제외한다.
