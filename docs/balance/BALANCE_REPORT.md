# 밸런스 시뮬레이션

## 실행 방법

`cd backend && gradlew.bat simulate --offline` (`check`에 포함되지 않음). 메인 DB 주소는 `-Dsimulation.url=...`로 바꿀 수 있고 기본값은 `jdbc:postgresql://localhost:5433/seoul_startup_sim`. 계정은 루트 `.env`의 `DB_USERNAME`/`DB_PASSWORD`.
시뮬레이터는 이 문서의 `simulation:begin`~`simulation:end` 표식 사이 표만 다시 쓰고, 위쪽 해설은 그대로 둔다. 업종별 원가율은 `V10__balance.sql`의 INSERT 문을 그대로 읽어 쓰므로 마이그레이션 값과 시뮬레이션 값이 어긋나지 않는다.

## 결론

| 단계 | 조정 내용 | 표준 정책 전체 생존율 | 업종별 표준 생존율 범위 |
|---|---|---:|---|
| 조정 전 (V9까지) | 없음 | 58.26% | 32.86% (커피) ~ 85.64% (한식) |
| 1차 (임대료만) | `rent.*` 15% 인하 | 61.00% | 35.27% (커피) ~ 86.86% (한식) |

- 2차 조정 후 10개 업종 모두 표준 정책 생존율이 목표 범위(대략 40~75%) 안에 들었다. 0%·100% 업종은 없다.
- 업종 간 순서는 같은 원가율(0.35, 임대료만 열)에서 나온 순서, 즉 실측 매출 자료만으로 생긴 순서를 그대로 유지했다: 한식 > 일식 > 제과 > 중식 > 양식 > 호프 > 패스트푸드 > 분식 > 치킨 > 커피. 원가율은 이 순서를 뒤집지 않는 선에서 간격만 좁혔다.
- 이 순서는 점포당 분기 매출 중앙값 순서와 대체로 같다. 예외는 매출 중앙값이 거의 같은 두 쌍(제과 3,788만 원·일식 3,664만 원, 패스트푸드 2,384만 원·호프 2,312만 원)으로, 중앙값이 아닌 상권별 분포(상위 상권의 이익 폭)가 생존율을 가른다.
- 전체 표준 생존율은 61.00%에서 60.22%로 거의 같다. 고매출 업종의 원가율을 올리고 저매출 업종을 내린 재분배라서 평균 난이도는 유지된다.

## 업종별 원가율과 근거

원가율은 계산기에서 "매출 대비 식재료비 비율"로 쓰인다(경영 능력치 보정 전). 출처 수치는 업종 중분류 단위(일반음식점, 기타 음식점업, 주점업, 비알코올 음료점업)까지만 공개돼 있어 서울시 상권 서비스 업종 10개와 1:1로 맞지 않는다. 그래서 각 값의 "근거" 칸에 출처 범위 안인지, 범위 밖의 게임 설정값인지를 적었다.

## 조정 판단

- 1차(임대료 15% 인하)는 고정비를 낮춰 전 업종을 비슷하게 올리므로 업종 간 격차(한식 87% vs 커피 35%)를 줄이지 못했다.
- 업종별 원가율은 매출에 비례하는 비용이라 매출이 큰 업종에 더 크게 작용한다. 그래서 고매출 업종은 올리고 저매출 업종은 내려 격차를 좁혔다. 다만 민감도가 작아서(원가율 0.05당 생존율 약 1~7%p) 양 끝 업종(한식, 치킨, 커피)은 실제 범위 밖 값이 필요했다.
- **실제 범위만 쓰면**(원가율 0.25~0.45 안) 한식은 최소 83.68%(0.45), 커피는 최대 38.95%(0.25)로 목표를 벗어난다(민감도 표). 사실성을 우선해야 한다면 이 대안도 가능하며, 이 경우 격차는 아래 제안처럼 원가율이 아닌 수단으로 줄여야 한다.
- 제안(이번 범위 밖, 구현하지 않음): 저매출 업종의 문제는 매출 대비 고정비(임대료 + 인건비 1,200만 원 + 마케팅)가 크다는 것이다. 업종별 임대료 계수(예: `rentFactor.<serviceCode>`, 카페·치킨의 작은 평수 반영) 또는 업종별 기본 인력 수가 원가율보다 사실적인 조정 수단이다. 둘 다 계산기 공식 변경이 필요하다.
- 임대료 15% 인하 근거는 이전과 같다: 원래 임대료는 실측 시세가 아닌 관리자 임의값이며 자치구 간 상대 순서는 유지한다.

## 한계와 후속

- **이벤트(전환점·순간·이웃 반응)는 시뮬레이터에 포함하지 않았다.** 계산기에 넣는 보정(modifier)이 0개인 상태의 통제 실험이며, 실제 게임에서는 전환점 선택 결과의 매출·원가율·임대료 보정이 생존율을 바꾼다.
- **후속: 전환점 빈도 점검.** 이벤트를 켠 데모(TASK-004B-1 진행 기록, 테스트용 가상 상권 1개)에서 8분기 중 전환점이 5회 나왔고 선택 결과가 모두 성공이었다. 현재 설정은 `event.fire.globalCap` 1, `event.fire.cooldownDefault` 4, `event.fire.minTurn` 1이다. 이 빈도와 보정 크기가 위 생존율을 얼마나 움직이는지는 시뮬레이터에 이벤트 엔진을 넣거나 분기별 기대 보정을 근사해 따로 측정해야 한다.
- 사장 능력치 40 고정, 경쟁점 밀집 보정 1 고정, 정책 3종 고정. 실제 플레이어의 선택 분포는 반영하지 않았다.
- 골든 회귀 테스트(4분기, 이벤트 8분기)는 V10 이전 설정을 테스트 리소스(`backend/src/test/resources/game/golden-settings.json`)로 고정해, 밸런스 값을 바꿔도 엔진 재현성 검증이 흔들리지 않게 했다.
- area 패키지는 API/수집 책임이 섞여 있고 동시 game 리팩터링과의 import 충돌을 피하려고 이동하지 않았다.
