## 0. 핵심 결론

1. 추정매출 `THSMON_SELNG_AMT`는 이름은 "당월"이지만 **분기(3개월) 합계**다. 월 단위가 필요하면 3으로 나눈다. 게임은 분기 단위라 그대로 쓰면 된다.
2. 영역-상권 좌표계는 **EPSG:5181**(Korea 2000 중부원점, FN=500000)이다. API는 중심점 X/Y와 면적만 주고, **폴리곤은 SHP 파일로만** 받을 수 있다. 1,650개 중 125개는 다중 파트라서 MULTIPOLYGON으로 넣어야 한다.
3. 상권은 **1,650개**(골목 1,090 · 발달 249 · 전통시장 305 · 관광특구 6), 서비스 업종은 **100개**(외식 10 · 서비스 47 · 소매 43)다.
4. 지금 받을 수 있는 자료(2021년 1분기 ~ 2026년 2분기)는 **모든 분기의 상권 코드 1,650개가 같다**. 2023년과 최신 분기를 비교하면 같은 코드 1,650개, 사라진 코드 0개, 새 코드 0개다. 변경 전 옛 코드는 더 이상 제공되지 않는다.
5. 매출 결측이 크다. **매출 행은 같은 업종 점포가 3개 이상인 조합에만 있다.** 점포가 있는 조합 중 매출이 있는 비율은 28.0%이고, 점포 3개 이상이면 67.7%, 외식 10개 업종에 점포 3개 이상이면 85.2%다. 업종 38개는 매출 자료가 아예 없다.
6. 임대료는 서울 열린데이터광장에서 **API나 파일로 받을 수 없다**. 골목상권 사이트의 임대시세는 화면으로만 볼 수 있다. 대안은 한국부동산원 상업용부동산 임대동향조사(R-ONE)인데, 공간 단위가 다르다.
7. 소상공인 상가 API는 JSON을 지원하고 페이지당 최대 1,000건이다. 서울 전체는 **552,422건이라 553회 호출, 하루 안에 끝난다**(일일 한도 10,000). 같은 내용이 **분기별 CSV 파일**(전국 zip 349MB, 서울 CSV 301MB, UTF-8)로도 제공된다.
8. `storeListByDate`로는 증분 수집을 할 수 없다. 데이터는 배포일(20260930) 한 날짜에만 있고 전국 2,753,776건이 모두 그 날짜로 나온다. 변경구분에 **삭제 값은 없다**(C 생성, U 수정). 그래서 DESIGN 9장의 "삭제 업소 포함" 설명은 근거가 없다.
9. 소분류 247개를 CS 100개에 매핑한 결과는 코드 수 기준 exact 50, manual 109, none 88이다. 서울 점포 수로 가중하면 exact 34%, manual 41%, none 25%다. 외식은 서울시 집계와 점포 수 비율이 0.77~1.11이라 잘 맞는다.
10. 카카오맵은 `kakao.maps.LatLng(위도, 경도)` WGS84를 쓰므로 5181 폴리곤을 **4326으로 변환한 뒤** 써야 한다.

### A-1. 응답 필드

**영역-상권 (11개)**: `TRDAR_SE_CD`(상권 구분 코드), `TRDAR_SE_CD_NM`, `TRDAR_CD`(상권 코드, 7자리), `TRDAR_CD_NM`, `XCNTS_VALUE`(X좌표), `YDNTS_VALUE`(Y좌표), `SIGNGU_CD`(자치구 5자리), `SIGNGU_CD_NM`, `ADSTRD_CD`(행정동 8자리, 행안부 주민등록 행정기관코드), `ADSTRD_CD_NM`, `RELM_AR`(영역 면적).
- `RELM_AR` 단위는 **㎡**다. 확인됨: SHP 폴리곤을 EPSG:5181 미터 좌표로 신발끈 공식 계산한 면적 ÷ `RELM_AR`의 최소~최대가 0.9999~1.0002다(`scripts/shp_area_check.mjs`). 범위는 1,854 ~ 2,462,734㎡.
- `XCNTS_VALUE`, `YDNTS_VALUE`는 EPSG:5181의 정수 미터값이고 X(동향)는 182,509~215,352, Y(북향)는 437,249~465,573이다. API는 숫자가 아니라 문자열로 준다.
- 상권 하나에 행정동이 하나만 붙어 있다(대표 행정동). 걸쳐 있는 행정동 목록은 주지 않는다.

**추정매출-상권 (55개)**: 키 7개(`STDR_YYQU_CD, TRDAR_SE_CD, TRDAR_SE_CD_NM, TRDAR_CD, TRDAR_CD_NM, SVC_INDUTY_CD, SVC_INDUTY_CD_NM`)와 금액 25개, 건수 23개.
- 금액: `THSMON_SELNG_AMT`, `MDWK_`/`WKEND_SELNG_AMT`, 요일 7개(`MON_ ~ SUN_SELNG_AMT`), 시간대 6개(`TMZON_00_06 ~ TMZON_21_24_SELNG_AMT`), 성별 2개(`ML_`, `FML_`), 연령대 6개(`AGRDE_10 ~ AGRDE_60_ABOVE_SELNG_AMT`)
- 건수: 같은 구성에 `_CO`가 붙는다(`THSMON_SELNG_CO` 등).
- 단위는 원이다(페이지 "※ 단위 : 원"). JSON에서는 **숫자형**이고 최댓값이 767,065,055,223이라 int32를 넘는다. **BIGINT 필요**(확인됨).

**점포-상권 (14개)**: 키 7개 + `SIMILR_INDUTY_STOR_CO`, `STOR_CO`, `FRC_STOR_CO`, `OPBIZ_RT`, `OPBIZ_STOR_CO`, `CLSBIZ_RT`, `CLSBIZ_STOR_CO`
- 이름이 헷갈리는 필드가 있다. Open API 명세는 `SIMILR_INDUTY_STOR_CO`를 "전체_점포_수", `STOR_CO`를 "일반_점포_수"라고 적고, CSV 헤더는 각각 "유사_업종_점포_수", "점포_수"라고 적는다.
- **확인됨**: `SIMILR_INDUTY_STOR_CO = STOR_CO + FRC_STOR_CO`가 20262의 75,912행 전부에서 성립한다. 또 점포-서울시의 20262 `SIMILR_INDUTY_STOR_CO` 합계 624,791이 골목상권 사이트 메인의 "점포수 전체 624,791개"와 같다. 따라서 **전체 점포 수 = `SIMILR_INDUTY_STOR_CO`**다.
- 개업률과 폐업률은 정수 %다. 표본 5건에서 `OPBIZ_STOR_CO / SIMILR_INDUTY_STOR_CO × 100`을 반올림한 값과 같았다(예: 6/156 = 3.8 → 4, 3/36 = 8.3 → 8). 전체 행 검증은 하지 않았다(**부분 확인**).
- 점포 0인 행이 492개 있다(`SIMILR_INDUTY_STOR_CO = 0`). 의미는 **미확인**이다(개업/폐업 기록 때문에 남아 있는 행일 수 있다는 추정).

**길단위인구-상권**: `TOT_FLPOP_CO`, 성별 2, 연령대 6, 시간대 6, 요일 7. 성별 합, 시간대 합, 요일 합이 모두 `TOT_FLPOP_CO`와 같다(표본 1행 확인. 요일 합은 반올림 차이 1).
- **`TOT_FLPOP_CO`의 단위(분기 합계, 일평균, 요일 합 중 무엇인지)는 미확인**이다. 골목상권 메인은 행정동 유동인구를 "일평균, 만 명"으로 보여주지만 상권 단위 값과 직접 맞춰 보지 못했다. 게임 안에서는 상대 비교(상권 간 순위, 비율)에만 쓰는 것을 권한다.

**직장인구-상권**: `TOT_WRC_POPLTN_CO`, 성별, 연령대 6, 성별×연령대 12(`MAG_*`, `FAG_*`).
- 공식 설명은 "1년 중 4분기에 한 번 갱신하고, 다음 해 1·2·3분기 값이 같다"이다. 확인됨: 2025년 1분기와 2분기 값이 1,641/1,641 상권에서 같다.

### A-3. 영역-상권 좌표계 → **EPSG:5181 (확인됨)**

- 데이터셋 페이지(OA-15560) 설명: "※ 좌표계 EPSG: 5181"
- SHP `.prj`: `Korea_2000_Korea_Central_Belt`, GRS80, TM, Central_Meridian 127, Latitude_Of_Origin 38, Scale 1.0, False_Easting 200000, **False_Northing 500000**. 이 값은 EPSG:5181과 같다(5186은 FN 600000, 5174는 Bessel 타원체).

- SHP 내용: Polygon(type 5) 1,650건, 링 1,786개, bbox X 182,079~215,473 / Y 437,150~466,040. **구멍이 있는 레코드 40개, 바깥 링이 2개 이상인 레코드 89개**(4건은 둘 다 해당, 다중 파트 레코드는 모두 125건)라서 `MULTIPOLYGON`이 필요하다. DBF 인코딩은 UTF-8(`.cpg`)이다. 필드명이 10자로 잘려 있다(`TRDAR_SE_C`, `TRDAR_SE_1`, `TRDAR_CD_N`, `XCNTS_VALU`, `YDNTS_VALU`, `SIGNGU_CD_`, `ADSTRD_CD_`).

### B-5. 좌표 (확인됨)

- 필드는 `lon`(경도), `lat`(위도)이고 **WGS84(EPSG:4326)**다. 가이드에 "WGS84기준 좌표값", 반경 조회 `cx`/`cy`는 "WGS84 좌표계 사용"이라고 적혀 있다. 실제 값 범위도 서울 경위도와 맞는다.
- 반경 조회 시 `cx` = 경도, `cy` = 위도다. 순서에 주의해야 한다.

## C. 카카오맵 (확인됨: https://apis.map.kakao.com/web/documentation/)

- `kakao.maps.LatLng(latitude, longitude)`는 "WGS84 좌표 정보를 가지고 있는 객체"다. `kakao.maps.Polygon`의 `path`는 `LatLng` 배열을 받는다. 내부 투영 기본값은 WCONG지만 입력은 WGS84 위경도다.
- 따라서 SHP(EPSG:5181) 폴리곤은 DB 적재 때 4326으로 변환하고, API 응답에서 `[lat, lng]` 배열로 넘긴다. GeoJSON의 `[lng, lat]` 순서와 반대라서 프론트에서 순서를 바꿔야 한다.

### 2. 테이블 컬럼 제안 (DESIGN 11장 보완)
- `trade_areas`: `area_code CHAR(7)`, `name`, `area_type CHAR(1)`(A/D/R/U), `area_type_name`, `district_code CHAR(5)`, `dong_code CHAR(8)`(대표 행정동), `area_m2 NUMERIC`(=`RELM_AR`, ㎡), `geom MULTIPOLYGON(4326)`, `centroid POINT(4326)`(API의 X/Y를 5181 → 4326으로 변환)
- `area_sales_q`: `sales_amt BIGINT`(**분기 합계**, 원), `sales_cnt BIGINT`, 필요하면 `weekday_amt`, `weekend_amt`, 시간대 6개(이벤트나 리포트용)
- `area_stores_q`: `store_cnt`(=`SIMILR_INDUTY_STOR_CO`, 전체), `general_cnt`(=`STOR_CO`), `franchise_cnt`, `open_cnt`, `close_cnt`, `open_rate SMALLINT`(%), `close_rate SMALLINT`(%)
- `area_population_q`: `floating_pop`(단위 미확인이라 상대 지표로만), `worker_pop`(연 1회 갱신, 1~3분기는 전년 4분기 값과 같음). `resident_pop`은 상주인구-상권(OA-15584, 이번 조사 범위 밖)에서 받아야 한다.
- `service_industries.category`는 코드 앞자리로 정한다(CS1 외식, CS2 서비스, CS3 소매). `has_sales BOOLEAN` 추가를 권한다(62개만 true).
- `industry_mappings`: `sbiz_small_code`, `service_code`(nullable), `match_type`, `note`, `reviewed BOOLEAN`
- `stores`: `sbiz_store_id`(`bizesId`)를 PK로 쓰고, `last_seen_version`을 둬서 새 스냅샷에 없는 업소를 폐업 처리
- 실제 상호(`bizesNm`)는 사실 정보 표시에만 쓴다(AGENTS 규칙 6).

### 3. 결측 정책 제안
- **창업 가능 업종은 매출이 있는 62개로 제한**하고, v1은 외식 10개부터 시작한다(외식은 점포 3개 이상 조합의 85%에 매출이 있다).
- (상권, 업종) 매출이 없을 때, 같은 업종 점포가 있으면 대체값을 쓴다: **같은 자치구, 같은 업종의 점포당 분기 매출 × 해당 상권 점포 수**(추정매출-자치구 OA-22176 사용. 자치구 데이터의 결측 여부는 미확인). 화면에는 "추정치"라고 표시한다.
- 같은 업종 점포가 0이면 매출 근거가 없다. 기본값은 "창업 불가"로 두거나, 자치구 평균 대체를 설정으로 켜고 끌 수 있게 한다.
- 매출 행이 하나도 없는 상권 84개(골목 61, 전통시장 23)는 v1에서 시작 상권 목록에서 뺀다.
- 결측 대체 여부는 `area_sales_q.is_imputed`(또는 별도 뷰)로 구분한다.

### 4. 좌표 변환
- 영역 SHP: EPSG:5181 → 4326. PostGIS의 `spatial_ref_sys`에 5181이 있는지 적재 테스트에서 확인해야 한다(Testcontainers PostGIS 이미지 기준 **미검증**).
- 상가 `lon`/`lat`: 이미 4326이므로 `ST_SetSRID(ST_MakePoint(lon, lat), 4326)`.
- 지도 응답: `[lat, lng]`(카카오 `LatLng` 순서). 화면 영역 조회 시 `ST_Simplify`는 5181(미터) 기준 허용오차로 단순화한 뒤 4326으로 변환하는 편이 다루기 쉽다(제안).

### 5. DESIGN 문서 수정 제안
- 9장 "`storeListByDate`(수정일자 기준, 삭제 업소 포함)는 증분 수집에 쓴다" → **근거 없음**. 삭제 구분이 없고, 배포일 하나에 전체가 찍힌다.
- 9장 "적재 후 확인할 것" 6개 항목은 이 문서의 A-2, A-3, A-6, A-7, A-8, B-4로 답했다.
- 8장 시장 규모: "단위 확인 후 분기 기준으로 환산" → `THSMON_SELNG_AMT`(분기 합계)를 그대로 쓴다.
- 4장 결산 카드 "상권 소식(개업, 폐업 수)": `OPBIZ_STOR_CO`, `CLSBIZ_STOR_CO`를 분기별로 쓸 수 있다(확인됨).
